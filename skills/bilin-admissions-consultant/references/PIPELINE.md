# pipeline.md 机制（详细规范）

主 SKILL.md 引用本文件。详细规则、模板、反模式都在这里。

## 它是什么

**pipeline.md** = 这个 case 的"持久化工作记忆"。

它解决的问题：长会话中 agent 容易忘记最初目标、重复 sub-agent 的工作、跳过调研、用户指错后又走回老路。pipeline.md 把"最重要、最不能丢"的信息从对话历史里提出来，写到一个用户可见、可编辑、可审查的 markdown 文件里。

不是 todo list。不是流水账。是**决策与约束的累积记录**。

## 何时创建

**Step 1 目标对齐完成后立即创建**。不是任务一开始就建（那时还不知道目标），也不是写到一半才想起来建（那时已经丢了上下文）。

放在学生工作目录下：`<student_dir>/pipeline.md`，不是 skill 目录下。每个 case 一份。

## 文件结构与硬上限

10 节固定结构。**总长 ≤ 200 行**。超过 200 行 = 你在写流水账，立刻精简。

```markdown
# pipeline.md · <学生姓名> · <创建日期>

## §0 元信息
- 学生：<姓名 / 年级 / 学校>
- 申请年份：<2028 入学>
- 创建日期 / 最后更新：<日期>
- 当前阶段：<目标对齐 / 信息盘点 / 调研 / 设计 / 写作 / 交付 / 复评>

## §1 北极星目标（永远不变）
<一句话写清最终目标。Jolin 案例：让妈妈看到孩子上藤校的希望，基于体系、策略和评估的希望，不是凭空的。>

**硬约束**：
- <例：所有数据可溯源，不能编造>
- <例：DOCX/PPT 必须含 Bilin logo 水印>

每次新对话开始，先读这一节，校准方向。

## §2 决策记录（append-only，不删历史）
| 日期 | 决策 | 理由 | 状态 |
|------|------|------|------|
| 2025-05-15 | 主 anchor 选 Brown ED，不是 Cornell | profile 匹配优先于录取率友好 | 已确认 |
| 2025-05-15 | 帆船从竞技冲刺降为保持竞争力 + soft support | D1 recruiting 不可能（教练判断 + ICSA 数据） | 已确认 |

方向变更必须在这里登记一行，写明"从 X → Y，原因 Z"。永远不删历史决策——被推翻的决策保留，状态改为"已推翻 (YYYY-MM-DD)"。

## §3 调研索引（防止重复调研）
| 主题 | 文件路径 | 一句话摘要 | 日期 |
|------|---------|----------|------|
| 帆船 D1/D3 recruiting | source_documents/帆船招生调研报告.md | D1 不可能，D3 低概率，全美每年仅 15-25 人获实质帮助 | 2025-05-15 |
| HKIS school profile | research/第一轮调研汇总.md | 3年32人进藤校，AP 体系，每届~190人 | 2025-05-15 |

调研前先扫这一节，避免重复跑 sub-agent 问已经回答过的问题。

## §4 Sub-agent 调用历史
| 日期 | 调用目的 | Sub-agent 类型 | 上下文文件 | 核心结论 |
|------|---------|--------------|-----------|--------|
| 2025-05-15 | Positioning 独立判断 | general-task-execution | 学生 6 份原始资料 | 推荐人文+视觉艺术双路径，劝退 Wharton/Stanford/MIT |
| 2025-05-15 | 调研框架设计 | general-task-execution | 学生资料 + 帆船调研 | 7 个调研方向，国籍是最大变量 |

## §5 已确认事实（白名单）
用户或客户明确确认过的事实。其他地方引用必须从这里取：

- 学生持香港护照，按 international student 申请（2025-05-15 用户确认）
- 学生主路径偏好：人文/历史/社科（基于 G5-G9 持续证据）

## §6 待确认事项（黑名单）
还没向客户确认的关键变量。在确认前不能写进交付物：

- [ ] G10 选课窗口与状态
- [ ] HKIS 同届 Ivy 申请者画像
- [ ] SAT 是否已开始诊断

## §7 红旗记录（不删）
项目过程中犯过的错或差点犯的错。永不删除——这是防"再犯"的疫苗：

- 2025-05-15: 用录取率友好选 Cornell anchor，被用户指出 profile 不匹配 → 改为 Brown
- 2025-05-15: 试图复用 pipeline 评估系统，被用户拉回"希望蓝图"定位

## §8 Open questions（待解）
当前还在悬而未决的问题，不属于上面任何一类：

- 视觉艺术作品是否达到 Brown "above-average" 标准？需要 G10 秋专业评估
- TASS 没录取的 Plan B 是否够强？

## §9 用户偏好与硬约束
用户在对话中表达过的偏好或约束。不要让 agent 忘记：

- 不要做冷冰冰的多维评分表，要像顾问在讲话
- 调研用 TinyFish，不用 WebSearch
- Sub-agent review 时不要给我的初步结论
- 大型交付分章节增量生成（fs_write + fs_append）

## §10 归档指针
当 §3 / §4 累积超过 30 行时，旧条目移到 `pipeline-archive-<日期>.md`，主文件留最近 10 条 + 链接。
```

## 操作规则（22 条）

### 会话生命周期（4 条）

1. **新对话开始 → 先读 pipeline.md** 的 §0、§1、§5、§6、§9。这 5 节决定"我现在在哪、不能违背什么、还在等什么"。
2. **每个 sub-agent 调用前 → 扫 §3 调研索引 + §4 调用历史**。如果已经问过，不要重复问。
3. **用户改方向 → 立刻在 §2 写一条变更记录**，再继续工作。不写 = 下一轮会忘。
4. **任务结束 / 暂停 → 更新 §0 当前阶段 + §8 open questions**，让下次接续的人（或下次的你）一眼知道在哪。

### 决策与方向（4 条）

5. **任何"我决定 X"的判断 → §2 登记**。理由不超过一行。
6. **被用户/sub-agent 推翻的决策 → 状态改 "已推翻"，不删原行**。被推翻的决策本身是信息，下次设计时要看到它，避免再走老路。
7. **方向漂移检测**：每生成 ≥ 1000 字内容前，回到 §1 北极星目标读一次。问自己"我现在做的还服务于这个目标吗？"
8. **不可逆决策（ED/EA、专业、路线大转弯）→ 必须在 §5 找到客户已确认条目**。找不到 = 立刻去问，不要硬推。

### 调研（3 条）

9. **任何调研完成 → §3 索引登记** 一行（路径 + 一句话摘要 + 日期）。摘要不超过 25 字。
10. **调研结论可能改变方向 → §2 写决策行 + §7 不写红旗**（除非它推翻了之前的决策）。
11. **调研文件本身写到 `research/` 或 `source_documents/research/` 目录，不写到 pipeline.md 内容里**。pipeline.md 只放索引。

### Sub-agent 配合（4 条）

12. **每次 sub-agent 调用 → 调用前扫 §4 历史 + 调用后写 §4 一行**。一行包含：日期 / 目的 / 类型 / 上下文文件 / 核心结论（≤ 30 字）。
13. **Sub-agent prompt 中可以引用 pipeline.md 的 §1（目标）、§3（已有调研索引）、§5（已确认事实）**。但**不要全文塞进 prompt**——sub-agent 拿到的应该是"路径 + 局部段落"，不是 pipeline 全文。
14. **早期独立判断类 sub-agent（positioning / review）→ 不要给它 §2 决策记录或 §7 红旗**。这两类信息会污染它的独立性。
15. **Sub-agent 默认只读 pipeline.md，不写**。它的产出由主 agent 拣选后写入。例外：明确委托 sub-agent 起草某节内容时，让它输出 patch 文本（oldStr/newStr），主 agent 应用。

### 写作交付（3 条）

16. **任何"写进交付物的事实"必须能在 §3 调研索引或 §5 已确认中找到来源**。找不到 → 标"待核实"，不写假数。
17. **大型交付（≥ 5000 字 / 多页 PPT）开工前 → §0 阶段改为"写作中"+ §8 加一条"当前 batch 进度"**。每完成一个 batch 更新这条。
18. **交付完成 → §0 阶段改为"已交付"+ §3 索引加一条最终产物**（路径 + 版本号）。

### 错误恢复（2 条）

19. **用户指出我犯了错 → §7 红旗加一条**（日期 / 错误描述 / 修正方向）。永不删。
20. **Agent 自己发现走偏 → 也写 §7**。承认偏差比掩盖更值钱。

### 维护（2 条）

21. **每次更新 pipeline.md 必须问自己**："这条更新能为下次 session 省至少 5 分钟吗？" 不能 → 不写。防流水账的硬规则。
22. **pipeline.md ≥ 200 行 → 立刻精简或归档**。§3 / §4 旧条目移到 `pipeline-archive-<日期>.md`。

## 反模式清单（10 条）

不要做以下事：

1. **流水账更新**——把每次 sub-agent 的完整输出粘进 pipeline.md。pipeline.md 只放索引和一句话摘要。
2. **超 200 行**——超过就是垃圾。立刻精简。
3. **写未经确认的推断**——§5 已确认只放用户/客户明确说过的话，agent 自己的推论放 §8。
4. **删除被推翻的决策**——历史决策是信息，永远保留并标"已推翻"。
5. **装饰美化**——加 emoji、表情、ASCII 横线、彩色标记都是浪费 token。pipeline.md 是工具，不是作品。
6. **重复信息**——一条事实只在一个地方写。其他地方需要时引用 §X 锚点。
7. **形式主义更新**——为了"看起来在维护"而更新没有信息量的内容。
8. **把 pipeline.md 当 todo list**——todo 是行动项，pipeline 是决策与约束。两者不同。
9. **Sub-agent 写 pipeline.md**——除非主 agent 明确委托并审核 patch，否则 sub-agent 不能直接修改 pipeline.md。
10. **用户没看过的"约定"写进 §5 已确认**——§5 必须有用户确认的痕迹（日期 + 出处）。

## Patch 协议（sub-agent 修订建议）

如果 sub-agent 给出 pipeline.md 修订建议，让它用以下格式输出：

```
## Patch for pipeline.md

### Patch 1
位置：§2 决策记录
oldStr: "<原文>"
newStr: "<新文>"
原因: <一句话>

### Patch 2
...
```

主 agent 收到后逐个 review 再 apply，不直接信任 sub-agent 修改。
